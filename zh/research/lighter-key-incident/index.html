交易密钥怎样走到了提现

原文问的是一把无对外提现权限的交易密钥，仍能给账户造成多大损失。答案还取决于三层约束。第一是交易和内转实际授权。第二是亏损会穿透哪些账户和抵押品。第三是平台中断后，哪些规则仍能保护余额和退出。六家平台会在不同层占优，总分会抹掉这些差别。

10:11 UTC 的以太坊交易看起来是一笔普通提现。决定资金去向的变化，发生在它上游。按 Lighter 的复盘，失陷的密钥能把抵押品转入受影响账户名下的公共池。另一个账户持有池份额，由此取得了新增抵押品的一部分索取权，再赎回份额，以自己的名义提款。提现直到链上结算都通过了所有者校验，但真正受益的账户已在中途变了。

把这条路径放到任何一家永续合约平台，都可以问三个问题。谁能签署操作？操作执行后，谁多了一笔可兑现的权益？正常运行或服务中断时，谁能把这笔权益变成实际付款？三个问题对应三层控制。只允许下单的密钥仍能通过成交与清算造成大额损失。有效性证明可以证明状态按规则变化。备用退出能否兑现，还要看用户能否拿到所需数据，并赶在权限或合约规则变化前提交请求。

这篇报告先沿着 Lighter 的资金路径复盘，再用同样的边界逐一检查 Hyperliquid、Aster、Variational、GRVT 和 Arcus，最后给出接入方与平台都可以复现的验收步骤。前往六平台对照 · 前往验收清单

签名如何泄露密钥

Lighter 将初始密钥泄露归因于交易者使用的非官方签名实现。同一把私钥为不同交易签名时重复使用了同一个秘密值。单份签名仍然有效，公开的多份签名放在一起，就可能暴露足以推导私钥的信息。平台称官方 SDK 和核心基础设施未受影响。复盘没有公开涉事签名器、构建版本或签名样本，无法进一步确定重用来自随机数生成、并发、进程重启还是其他路径。平台技术复盘

用 Schnorr 常见的加法记号说明，签名标量可写成 s = k + e·x。k 是秘密 nonce，e 是该消息与承诺对应的公开挑战值，x 是私钥。两条不同消息使用同一个 k 且挑战值不同时，相减就会消去 k，从而在标量域内求出 x = (s₁ − s₂) / (e₁ − e₂)。这里用示意记号解释这类故障。复现数学关系无需获取受影响的实际签名或密钥。

签名 nonce 与交易 nonce 分别保护什么
字段作用错误表现
签名 nonce作用签名器内部生成的一次性秘密值。参考实现采用 ECgFp5 曲线上的 Schnorr 签名和基于 Poseidon 的哈希。错误表现同一私钥对不同消息复用秘密值，两份签名共享一个代数项。两次签名的挑战值各自不同，消去共享项后可能推导出私钥。
交易 nonce作用按 API 密钥维护的请求序号，可通过 SDK 或平台 API 查询。错误表现过期或次序错误的请求会被拒绝。拿到私钥的人可以选用新的序号来签署新请求。

签名验证能确定哪把密钥提交了授权。Rollup 证明能验证状态变化是否符合程序实现的规则。私钥一旦泄露，攻击者照样可以生成有效签名，协议也就可能证明一笔密钥合法持有人从未授权的状态变化。公开证据指向授权凭证的泄露，以及它在这套规则下能够触达的资金。官方签名 SDK · Schnorr 参考实现 · API 密钥范围与序号

比较六家 API 时，先把凭证、编码和权限分开。HMAC 用共享秘密认证。EIP‑712 规定结构化消息的编码和域，ECDSA 用于签名。Ed25519 属于 EdDSA。请求的重放限制和授权边界仍要由各自实现核对。Lighter 官方签名库被原文核验的版本使用安全随机源，具体风险出在复用了秘密 nonce 的第三方签名器。 HMAC 规范 · EIP‑712 · EdDSA 规范 · 固定版本签名器

公共池改变了受益人

按照 Lighter 文档，常规安全提现只能付到该账户所有者的 L1 钱包。可付到其他地址的快速提现，以及跨所有者划转，则同时要求 API 授权和账户所有者的 L1 钱包签名。事发时，受影响账户自己的公开池被划转规则视为同一所有者的目的地，其他账户仍可持有该池的份额。划转检查的是池账户归谁，赎回检查的是谁有权提走池里的价值。两道检查各自通过，组合起来却可以把抵押品分配给另一个账户。提现与划转规则 · 平台复盘中的资金路径

用一组假设数字看份额的变化。池中有 100 单位资产、100 份份额，另一个账户持有其中 25 份，原本可以赎回 25 单位。再向池里转入 900 单位而不增发份额，每份价值便从 1 升到 10。另一个账户仍持有 25 份，能赎回的价值却从 25 升到 250 单位，增加了 225。池内记账依然平衡，每份资产定价也一致，改变的是谁有权领取这笔价值。这个例子假设可即时按比例赎回，且没有手续费、账面损失或延迟。

审计这类规则时，可以把划转、份额发行与赎回、费用、最终提现连成一条路径，沿途检查各方可领取的净额。单笔交易只看目的账户的归属，会遗漏由份额产生的外部请求权。这个案例里，授权检查需要覆盖向有外部持有人享有赎回权的池划入资金。

Guardian 与后续修复

平台先公告暂停提现和创建池，随后披露已在合约上启用 Guardian 模式，并评估另一次提现尝试。复盘称安全委员会在暂停期间向受影响的交易者归还了约 500 万 USDC，解除 Guardian 后恢复提现。公告和复盘可以核对处置顺序，具体资金差额仍需账户余额与结算凭证。事件进展 · 平台复盘

Arcus、HyprEarn 与 Aster

Arcus · 虚增的账本余额抵达真实的提现桥

Arcus 的事故报告记载，美东时间 2026 年 11 月 9 日约 22:07，一个账户利用子账户间的内部转账缺陷，记出了高于实际持有资产的余额。22:10，提现桥的链上限流拦下约 300 万美元的后续请求。Arcus 称，这批请求没有出款，后来已撤销。23:07，全平台暂停提现，此前已有 2,234,391 USDG 在链上实际出款。Arcus 称其金库补足了缺口。核对事故影响时，应将已出款、被拦截请求和金库补款分开记账。 Arcus 事故报告

内部转账要维持账本上的价值守恒，提现桥也要对看似有效的余额独立执行出款规则。两道控制各自可能失效。账本虚增之后，下游限流仍能压低给定时间内的出款上限。持续发起请求、并行使用多个账户、各资产使用独立额度，或特权路径绕开限额，都可能改变这个上限。

记初始可用额度为 C，每分钟补充额度为 r，截至第 t 分钟的累计请求金额为 D(t)。模型假设每笔出款都经过同一个令牌桶，所有执行者都受其约束。此时累计出款最多为 min(D(t), C + r × t)。到第八分钟，累计请求 800 万美元，出款上界为 400 万美元。若实现会整笔拒绝或排队，出款额可能更低。如果用美元给多种资产设统一上限，还要核对估值来源、价格过期的处理，以及额度在哪个阶段占用：申请、预留还是最终结算。

HyprEarn · 停用第三方集成之后，还要检查交易场所的授权

11 月 14 日，HyprEarn 称，正在调查少量已批准其代理钱包的 Hyperliquid 账户出现未经授权交易的报告。公告要求用户在交易场所移除旧代理，因为授权会保留到用户移除为止。公告未给出损失金额，也未确认签名权限是如何被使用的。确认集成已断开时，应在交易场所核对授权、成交和当前仓位。按 Hyperliquid 的权限模型，代理钱包即使无权调用提现接口，仍能通过获准的订单造成交易损失。 HyprEarn 安全公告 · Hyperliquid 代理钱包文档

Aster · 用户报告了内部划转，签名和资金路径仍待核实

11 月 16 日至 17 日，媒体援引一位用户发布的材料称，北京时间 11 月 13 日凌晨发生的七笔内部划转合计约 456 万 USDT，与名为 aster-desktop 的浏览器生成凭证有关。报道也提到交易场所已介入调查。要确认实际签名者、经过的权限判断和最终资金去向，需要账户流水、执行时的授权记录和结算凭证。用户还称接收账户随后发生提现，原账户中涉及 33 BTC 的资产发生交易。核算实际损失需要把内部记录和这些后续事件逐笔对应，并区分卖出、换汇、费用和桥接结算。现有材料无法独立确认完整资金路径、协议漏洞，或凭证执行时的实际权限。核对时应分别沿交易场所的授权逻辑追踪浏览器凭证、受管交易密钥和主账户签名。 BlockBeats 报道 · ChainCatcher 报道（Binance News 转载）

场所工程团队 · 分别约束账本与出款

在写入状态时核对主账户、子账户、签名者、操作、资产与最终受益人。测试内部划转和手续费是否守恒，小额和边界金额的舍入，以及提现额度从预留到支付、撤销或过期是否走同一套状态规则。将幂等键与结算结果一起记录，避免重试导致重复支付或将已支付的金额退回。对账户别名、跨链队列、运维和紧急入口执行相同的不变量检查。

提现预算应经得起许多账户并行使用。能统一限额的场所可以同时设账户、资产和全局上限，并把已批准尚未结算的请求算入额度。对净流出异常、可兑余额骤增、账本与结算不符等情况设置自动控制和人工升级路径。公布紧急暂停的影响范围，以及用户在停机期间撤单或退出的前提。明确应用、撮合引擎、自动执行服务、桥接转发者和管理员分别故障时，哪些防线仍然有效。

市场运营与治理 · 演练生效、恢复和退出

记录谁能修改预言机来源、管理员权限、提现上限、合约版本和暂停状态。检查同一方是否可以同时发起、批准和执行变更。将真实部署合约中的紧急权限、时间锁和例外一并核对，并把实际变更延迟与用户取得状态、生成证明和退出所需时间对照。退出路径需要独立演练和计时。

在应急手册写明告警、取证要求、执行权限和恢复处理排队请求的条件。确认暂停时哪些订单仍能增加风险，在支持只减仓的情况下这类指令如何处理，以及谁负责在恢复前完成对账。在测试环境注入异常输入和故障，记录测试部署与生产配置的差异。

四项安全验收

演练前写清通过条件。譬如撤权生效后由旧签名者签发的新请求必须被拒绝，已经排队的旧请求则要按其状态明确结局。验证提现桥时，按配置核对账本和出款不变量，分别显示申请、实付、撤销和仍在途的金额。演练独立退出时，记录状态数据从哪里取得、由谁提交交易、全程耗时，以及日常数据提供方下线后能否完成证明。

为每次验收记录日期、场所、网络、功能、客户端或 SDK 版本、可见的合约部署或功能版本、签名者角色，以及账户或市场类型。保留请求引用、交易引用、预期规则和结果，避免在共享日志里留下私钥、凭证或个人账户信息。配置发生变化或新增出款路径后，重跑受影响的项目。

公开材料留下了一些待验证的路径。事故公告记录发布方的说法和动作时间，链上转账能证明结算是否发生。要归因到上游决策，还需要核对签名与场所的授权记录。涉及委派权限时，应核对执行当时的授权范围、成交记录和审批历史。涉及账本时，应追到包含撤销与金库补款的完整对账。只有把这些记录串起来，才能判断新加的控制能否覆盖已出现的故障。

量化团队要按权限核对保证金实际隔离，并把不合理报价、杠杆变更和一条腿被减仓纳入告警。只读的 AI 或跟单工具可以从公开地址或查看权限起步，停用交易工具后，应在平台端收回凭证。大额保证金账户还要给存量仓位留压力缓冲，并实测前端关闭时所需的状态、等待时间和退出步骤。
